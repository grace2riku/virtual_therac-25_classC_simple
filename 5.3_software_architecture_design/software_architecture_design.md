## 3. ソフトウェア要求事項のソフトウェアアーキテクチャへの変換(箇条 5.3.1)

SRS の全要求事項(SRS-001〜010、SRS-101、SRS-RCM-001〜004)を、ソフトウェア項目 ARCH-001 とその 3 つのソフトウェアユニットへ割り当てる。割付は「11. トレーサビリティマトリクス」に示す。

## 4. ソフトウェアアーキテクチャの概要

### 4.1 アーキテクチャ方針
- 採用するアーキテクチャスタイル: **レイヤード(3 層)**。共通基盤層 → 防御判定層 → 制御層の単方向依存とする。
- 採用理由: 安全判定(SafetyInterlock)を制御フロー(TreatmentSequencer)から独立させ、依存方向を一方向に固定することで、安全判定が制御層の状態に汚染されないようにする。最小構成のため単一ライブラリ・単一プロセスとする。

### 4.2 全体構成図

```
        操作者コンソール (CppUTest 試験ドライバが模擬)
                    │  IF-E-001 (th25s_seq_* 公開 API)
                    ▼
   ┌─────────────────────────────────────────┐
   │  制御層     ARCH-001.2 TreatmentSequencer  │  ← 治療シーケンス状態機械
   └───────┬─────────────────────┬─────────────┘
           │ IF-U-001            │ IF-U-002
           ▼                     ▼
   ┌──────────────────┐  ┌──────────────────────┐
   │ 防御判定層         │  │ 共通基盤層              │
   │ ARCH-001.3        │  │ ARCH-001.1            │
   │ SafetyInterlock   │─▶│ CommonTypes           │
   │ (純関数・状態なし) │  │ (型・検証・飽和カウンタ) │
   └──────────────────┘  └──────────────────────┘
              IF-U-003
   依存方向は常に上位→下位の一方向。CommonTypes は他に依存しない。
```

### 4.3 ソフトウェア項目一覧

| 項目 ID | 名称 | 分類 | 安全クラス | 概要 |
|---------|------|------|----------|------|
| ARCH-001 | TH25S-CORE 安全コア | 項目 | C | ビームインターロックの全機能を担う静的ライブラリ |
| ARCH-001.1 | CommonTypes(UNIT-001) | ユニット | C | 共通型・モード別範囲検証・飽和カウンタ・エラーメッセージ |
| ARCH-001.2 | TreatmentSequencer(UNIT-002) | ユニット | C | 治療シーケンス状態機械。操作順序を構造的に強制する |
| ARCH-001.3 | SafetyInterlock(UNIT-003) | ユニット | C | ビーム照射可否の独立した最終整合性判定(純関数) |

> 本プロジェクトは単一ライブラリ・3 ユニットの最小構成である。ARCH-001 全体をクラス C とする(SSC-TH25S-001 §7.3)。

## 6. SOUP の識別

| SOUP ID | 名称 | バージョン | 用途 | 入手元 | ライセンス |
|---------|------|----------|------|--------|----------|
| SOUP-001 | CppUTest | 4.0 | ユニット試験フレームワーク(既定) | パッケージマネージャ(Homebrew / apt) | BSD-3-Clause |
| SOUP-002 | GoogleTest | 1.17.0(Homebrew)/ libgtest-dev 提供版(apt) | ユニット試験フレームワーク(任意選択、CR-0001 で追加) | パッケージマネージャ(Homebrew / apt) | BSD-3-Clause |

> SOUP-001 / SOUP-002 はいずれも **試験コードのみにリンクされ、製品成果物(`libth25s_core.a`)には一切リンクされない**。製品の動作には寄与しない。両 SOUP は相互排他で選択する(CMake オプション `TH25S_TEST_FRAMEWORK=cpputest|gtest|both`、`both` 選択時は別実行ファイルとして共存し、同一の試験ケース集合をそれぞれが実行する)。

## 9. リスクコントロール手段のためのソフトウェア項目の分離(箇条 5.3.5 ― クラス C)

| 分離 ID | 対象項目 | 分離手段 | 分離の根拠・検証方法 |
|--------|---------|---------|--------------------|
| SEP-001 | ARCH-001.3 SafetyInterlock を ARCH-001.2 TreatmentSequencer から分離 | **論理分離**: (1) 別翻訳単位(`safety_interlock.c`)、(2) 可変なグローバル状態・静的状態を一切持たない純関数として実装、(3) TreatmentSequencer の内部構造体に依存せず、判定に必要な全情報を引数 `th25s_interlock_input_t` で受け取る | TreatmentSequencer の状態管理に欠陥があっても、SafetyInterlock が独立に不整合照射を拒否できる(多重防御)。検証は UT-003-14(純関数性)および UT-002-13/14(結合状態での独立判定)で行う。 |

> **分離の限界の明示:** 本シンプルプロジェクトは学習目的のため、プロセス分離・MPU 等の **物理分離は適用しない**。SEP-001 は論理分離に留まる。したがって IEC 62304 5.3.5 に従い、ARCH-001 配下の全項目を同一(最高)の安全クラス **C** として扱う(SSC-TH25S-001 §7.3)。論理分離はリスク低減(多重防御)には寄与するが、安全クラス低減の根拠とはしない。
