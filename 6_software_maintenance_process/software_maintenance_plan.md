## 1. 目的と適用範囲

本書は、IEC 62304 箇条 6(ソフトウェア保守プロセス)に基づき、リリース後の TH25S-CORE に対する保守活動の計画を定義する。フィードバック収集から問題分析、修正実装、再リリースまでを対象とする。

## 3. ソフトウェア保守計画の確立(箇条 6.1)

### 3.1 保守の目的
- リリース済みソフトウェアに対する問題報告・変更要求を体系的に処理する。
- 修正版を初回リリースと同等の品質・安全水準で提供する。
- リスクマネジメントファイルを継続的に最新に保つ。

### 3.2 保守プロセスの構成
| 活動 | 参照条項 | 責任者 |
|------|---------|-------|
| 問題・修正の分析 | 6.2 | 開発者A |
| 修正の実施 | 6.3 | 開発者A |
| リスクマネジメント再評価 | 7.4、ISO 14971 | 開発者A |

### 3.3 開発プロセスと保守プロセスの関係
- 保守活動で新規開発・大規模改修を行う場合は、該当部分について箇条 5 のプロセスを再適用する。
- 軽微な修正も、箇条 8(構成管理)と箇条 9(問題解決)のプロセスに従って管理する。

## 4. 問題及び修正の分析(箇条 6.2)

### 4.1 フィードバックの監視(箇条 6.2.1.1)
| チャネル | 方法 | 頻度 | 責任者 |
|---------|------|------|-------|
| 問題報告 | GitHub Issues(問題報告テンプレート) | 随時 | 開発者A |
| CI 結果 | GitHub Actions(docs-check / build-test) | push/PR ごと | 開発者A |
| SOUP 供給元情報 | CppUTest の公開リポジトリ・リリースノート | リリース時 | 開発者A |

### 4.2 フィードバックの文書化及び評価(箇条 6.2.1.2)
すべてのフィードバックは GitHub Issues に登録し、再現性・影響を受けるバージョン・安全性影響・既知の残留異常との関連の観点で評価する。

### 4.3 問題報告の安全性影響評価(箇条 6.2.1.3)
各問題報告は、リスクマネジメントプロセス(箇条 7.4)へ入力し、新たなハザード又は既存ハザード(HZ-001〜003)の再評価要否を判断する。

| 判定 | 処置 |
|------|------|
| 安全性影響あり | RMF-TH25S-001 を更新し、SRMP §6 に従い変更のリスクマネジメントを実施 |
| 安全性影響なし | 通常の問題解決プロセス(SPRP)で処理 |

### 4.4 ソフトウェア問題解決プロセスの使用(箇条 6.2.2)
問題報告の処理は、箇条 9(SPRP-TH25S-001)に従う。

### 4.5 変更要求の分析(箇条 6.2.3)
変更要求は以下の観点で分析する。

- [ ] 変更内容と目的
- [ ] 影響を受けるソフトウェアユニット(UNIT-001〜003)
- [ ] 関連する SRS・設計・試験・リスクコントロール手段(RCM)
- [ ] 患者・使用者への影響

### 4.6 変更要求の承認(箇条 6.2.4)
変更要求は CCB(CCB-TH25S-001)で審議し、承認された要求のみ実施に進める。本プロジェクトは単独開発のため、CCB は開発者A が擬制する(SCMP §4.1.1)。

| 変更区分 | 承認者 |
|---------|-------|
| 軽微(文書のみ、コメント修正) | 開発者A(開発責任者として) |
| 中程度(非安全関連機能の修正) | 開発者A(CCB 簡易審議を擬制) |
| 重大(安全関連、アーキテクチャ変更) | 開発者A(CCB 正式審議を擬制。24 時間以上のインターバルを設ける) |

### 4.7 ユーザ及び規制当局への伝達(箇条 6.2.5)
本プロジェクトは学習目的の仮想プロジェクトであり、実際のユーザ・規制当局は存在しない。伝達プロセスの体験として、安全関連修正時はリリースノート(GitHub Releases)へ記載し、変更要求台帳(CRR)§6 にユーザ通知要否を記録する枠組みを擬制する。

## 5. 修正の実施(箇条 6.3)

### 5.1 確立されたプロセスによる修正実施(箇条 6.3.1)
| 修正規模 | 適用ステップ |
|---------|-----------|
| 軽微 | 実装 → ユニット試験 → 構成管理 |
| 中程度 | 詳細設計 → 実装 → ユニット・結合試験 → 構成管理 |
| 重大 | 要求分析 → アーキテクチャ → 詳細設計 → 実装 → 全試験 → リスク再評価 → 構成管理 |

### 5.2 修正済みソフトウェアの再リリース(箇条 6.3.2)
修正版のリリースは箇条 5.8 のプロセスを適用する。少なくとも以下を実施する。

- [ ] 回帰試験(影響範囲に応じたレベル。安全関連は全 RCM 検証ケースを再実行)
- [ ] リスクマネジメントファイル(RMF)更新
- [ ] ソフトウェアマスタ仕様書(SMS)の改訂版作成
- [ ] 既知の残留異常一覧の更新
- [ ] `DEVELOPMENT_STEPS.md` への保守ステップ追記
