## 1. 目的と適用範囲

本規程は、IEC 62304 箇条 8.2(変更制御)に基づき、変更管理委員会(CCB: Change Control Board)の構成・運営・意思決定手順を定義する。本規程は TH25S-CORE のソフトウェア・ドキュメント・SOUP・ツール・試験資産に対するすべての変更要求(CR)に適用する。

## 3. CCB の構成

### 3.1 単独開発下の擬制
本プロジェクトは単独開発の学習プロジェクトであり、CCB の全役割(議長・書記・開発責任者・試験責任者・リスクマネジメント責任者)を **開発者A が兼任して擬制** する。これは Therac-25 事故の主要因「単独開発者 + 独立レビューの不在」を学習目的で意図的に補うものである。独立性は §5.4 の審議インターバルと CI による機械的検証で代替する。

### 3.2 役割
| 役割 | 責任 | 担当 |
|------|------|------|
| 議長 | 会議運営、最終承認 | 開発者A |
| 書記 | 議事録、CR 台帳(CRR)更新 | 開発者A |
| 技術影響評価 | 技術的影響範囲の評価 | 開発者A |
| 検証影響評価 | 回帰試験範囲の評価 | 開発者A |
| 安全性評価 | RMF 更新要否の評価 | 開発者A |

## 4. CR の起票と受付

### 4.1 起票時の記載項目
CR は GitHub Issues(変更要求テンプレート)で管理し、以下を記載する。テンプレートの実体は [`.github/ISSUE_TEMPLATE/change-request.yml`](../.github/ISSUE_TEMPLATE/change-request.yml)(YAML Issue Forms 形式)であり、GitHub の Issue 起票画面で「変更要求 (CR / Change Request)」を選択すると本テンプレートが適用される。

**最低記載項目(本テンプレートで起票時に必須化):**

- CR ID(`CR-NNNN`)
- 起票者、起票日
- 変更対象(CI ID、ファイルパス)
- 変更理由(関連する問題報告 PRB-ID、保守要求)
- 変更概要
- 初期重要度区分(軽微 / 中程度 / 重大)

**追加で本テンプレートが収集する項目(本規程 §5.2 / §7、SCMP §4.3、SMP §4.7 連携):**

- 安全関連性チェック(本規程 §5.2 の 5 項目チェックリスト。1 つでも該当すれば MAJOR 区分必須)
- 検証方針(SCMP §4.3 規模別検証に従う)
- ロールバック計画(本規程 §7「ロールバック計画の実施可能性」)
- ユーザ通知の要否(SMP §4.7)
- 規制当局通知の要否(IEC 62304 §6.2.5)

> **学習プロジェクトの教材的補足:** GitHub Issue Forms の `validations.required` 機能により、上記必須項目は起票時点で機械的に補強される。これは「単独開発下の独立性擬制」(§3.1)を補強する機械的検証の一形態として位置付ける(CI による検証と並ぶ第 4 の独立性代替手段)。

## 5. CR の分類と承認フロー

### 5.1 区分定義
| 区分 | 定義 | 承認フロー |
|------|------|----------|
| 軽微(MINOR) | コメント修正、誤字、文書のみの軽微修正 | 開発者A(開発責任者として)承認 |
| 中程度(MODERATE) | 非安全関連機能の修正・追加 | CCB 簡易審議(擬制) |
| 重大(MAJOR) | 安全関連機能、アーキテクチャ変更、SOUP 変更 | CCB 正式審議(擬制) |

### 5.2 分類判定の基準
以下のいずれかに該当する場合は **重大(MAJOR)** と判定する。

- [ ] リスクコントロール手段(RCM-001〜004)を実装する CI(UNIT-001〜003)への変更
- [ ] ソフトウェア安全クラスに影響し得る変更
- [ ] 分離設計(SEP-001)に影響する変更
- [ ] 外部インタフェース(IF-E-001)の変更
- [ ] SOUP(CppUTest)の追加・削除・バージョン変更

### 5.3 承認フロー図

```
[CR 起票 (GitHub Issue)]
    │
    ▼
[区分判定]
    ├─ 軽微   → [開発者A 承認] → [実装] → [検証] → [クローズ]
    ├─ 中程度 → [CCB 簡易審議(擬制)] → [承認/却下] → [実装] → [結合試験] → [クローズ]
    └─ 重大   → [審議インターバル ≥ 24h] → [CCB 正式審議(擬制)]
                  → [リスク再評価(SRMP §6)] → [実装] → [全試験] → [CCB 完了確認] → [クローズ]
```

### 5.4 審議インターバルの運用

単独・小規模開発では、複数名 CCB の「時間差による独立視点の再検討」を擬制するため、意図的なインターバルを設ける。

| プロジェクト種別 | 推奨インターバル | 本プロジェクトの採用値 |
|---------------|--------------|--------------------|
| 学習・デモプロジェクト | 1 分以上 | — |
| 小規模単独開発(実機未搭載) | 数時間 | **中程度区分: 数時間** |
| 医療機器実機搭載プロジェクト | 24 時間以上 | **重大区分: 24 時間以上**(本プロジェクトは学習目的だが、安全クラス C の慣行を体験するため重大区分には 24 時間以上を採用) |

#### 5.4.1 例外
- **軽微区分** はインターバル対象外。
- **重大区分** でも、安全性影響のある重大不具合のホットフィックスは議長判断でインターバル短縮可(理由を PR 本文に明記)。

## 6. CCB 会議の運営

本プロジェクトは単独開発のため、CCB 会議は Pull Request 上の自己審議として運営する。議事は PR 本文・コミットメッセージ・CRR への記録をもって議事録とする。

### 6.1 議事進行(PR 上で擬制)
1. 新規 CR の審議(区分判定・承認・却下)
2. 進行中 CR の状況確認
3. 閉会した CR の完了確認(CRR の状態更新)

## 7. 審議の観点

各 CR は以下の観点で審議する。

- [ ] 変更の必要性・妥当性
- [ ] 技術的影響範囲(依存する CI、回帰試験範囲)
- [ ] 安全性への影響(RMF 更新の要否、HZ-001〜003 への影響)
- [ ] ロールバック計画の実施可能性

## 8. 決定の記録

CCB の決定は変更要求台帳(CRR-TH25S-001)§4 に記録する。記録項目: 決定日・CR ID・決定種別(承認 / 条件付き承認 / 却下 / 保留)・条件・関連コミット。
