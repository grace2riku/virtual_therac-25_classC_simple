## 1. 目的と適用範囲

本書は、IEC 62304 箇条 9(ソフトウェア問題解決プロセス)に基づき、開発中および市販後に発見された TH25S-CORE の問題を記録・分析・解決・検証する一連の手順を定義する。

> **ID 規則:** 問題報告 ID は `PRB-NNNN` を使用する(`PR-NNNN` は使わない)。GitHub の Pull Request と区別するためである。

## 3. 問題報告の作成(箇条 9.1)

### 3.1 トリガ
以下のいずれかが発生した場合、問題報告(PRB-NNNN)を作成する。

- 試験(ユニット・結合・システム)での不合格
- コードレビュー・設計レビューでの指摘
- CI(docs-check / build-test)の失敗
- SOUP(CppUTest)の脆弱性・異常公開情報
- 市販後フィードバック(本プロジェクトでは GitHub Issues)

### 3.2 問題報告の最低記録項目
| 項目 | 内容 |
|------|------|
| 問題報告 ID | PRB-NNNN |
| 報告者 / 報告日 | 氏名 / ISO 8601 日付 |
| 問題の概要 | — |
| 発見時のソフトウェアバージョン | コミットハッシュ / タグ |
| 発見時の環境 | OS / コンパイラ / 試験環境 |
| 再現手順 | — |
| 期待される動作 / 実際の動作 | — |
| 重大度(初期判定) | Critical / Major / Minor |
| 関連資料 | ログ、試験 ID(UT/IT/ST) |

## 4. 問題の調査(箇条 9.2)

### 4.1 調査項目
- [ ] 問題の再現性
- [ ] 根本原因(設計誤り / 実装誤り / 要求誤り / SOUP 起因 / 環境依存)
- [ ] 関連するソフトウェアユニット(UNIT-001〜003)
- [ ] 影響を受けるリリース・構成
- [ ] **患者・使用者・第三者の安全への影響評価**(リスクマネジメント入力。HZ-001〜003 への影響を判定)

### 4.2 調査記録
調査者・調査期間・再現結果・根本原因分析・影響範囲・安全性影響を GitHub Issue 上に記録する。

## 5. 関係者への通知(箇条 9.3)

| 通知先 | トリガ | 通知手段 |
|-------|-------|---------|
| 品質責任者(開発者A が擬制) | 全問題 | GitHub Issue |
| CCB(開発者A が擬制) | 修正を要する問題 | CCB 審議(PR 上で擬制) |
| ユーザ・規制当局 | 安全性影響のある問題 | 本プロジェクトは学習目的のため擬制。SMP §4.7 の枠組みに従い、リリースノートへの記載で代替 |

## 6. 変更管理プロセスの使用(箇条 9.4)

解決のための変更は、箇条 8 の構成管理プロセス(SCMP)に従って実施する。

```
問題報告 PRB-NNNN → 変更要求 CR-NNNN を起票 → CCB 承認(擬制) →
  実装 → 検証 → マージ → リリース
```

- コミットメッセージ・Pull Request・リリースノートに `PRB-NNNN / CR-NNNN` を明記する。

## 7. 記録の維持(箇条 9.5)

問題報告とその解決記録は、以下とともに構成管理下(Git リポジトリ + GitHub Issues)に保管する。

- 当初の問題報告(3 章)
- 調査結果(4 章)
- 関連する CR と変更内容
- 検証結果(試験 ID、カバレッジ影響)
- クローズ日、クローズ承認者

## 8. 問題の傾向分析(箇条 9.6)

### 8.1 分析頻度
- リリースごと(本プロジェクトでは初回リリース時点で問題報告 0 件)。

### 8.2 分析項目
- ユニット別・フェーズ別の発生件数
- 根本原因分類(設計 / 実装 / 要求 / SOUP / 環境)
- 再発(類似原因)の有無
- 安全性影響のあった問題の件数

### 8.3 フィードバック
分析結果に基づき、開発標準(コーディング規約)・試験計画(追加試験ケース)を見直す。傾向データは変更要求台帳(CRR)§7 と連携する。

## 9. ソフトウェア問題解決の検証(箇条 9.7)

すべての修正について、以下を検証する。

- [ ] 問題が解消されたこと(修正前に失敗していた再現試験が、修正後に合格すること)
- [ ] 新たな不具合を導入していないこと(回帰試験。CI で全 55 試験を再実行)
- [ ] リスクコントロール手段(RCM-001〜004)の有効性が維持されていること
- [ ] 構成管理・ドキュメントが整合していること

検証合格後、問題報告を「解決済(CLOSED)」としてクローズする。

## 10. 試験文書の内容(箇条 9.8)

問題解決に伴う試験文書には以下を含める。

1. 試験対象の問題報告 ID / CR ID
2. 対象ソフトウェアバージョン(修正前・修正後のコミットハッシュ)
3. 再現試験の手順と結果(修正前の失敗、修正後の合格)
4. 回帰試験の範囲と結果
5. リスクコントロール手段の再検証結果(該当時)
6. 試験環境とツールバージョン
7. 実施日、実施者、承認者
